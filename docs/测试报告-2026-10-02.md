### L3a —— 14× 提速确认（4096×4096 自注意力）

| 实现 | 耗时 | 等效算力 |
|---|---|---|
| SDPA 默认（→ mem-efficient） | **825.44 ms** | 0.12 TFLOP/s |

### L3b —— 前两例与手册吻合，第三例脚本报错

| 用例 | 耗时 | 峰值显存 |
|---|---|---|
| TRELLIS.2 cross（blocks fp16） | **4.563 s**（手册 ~4.7 s ✅） | 3429 MiB |
| Pixal3D proj | **4.816 s** | 3542 MiB |
| Pixal3D cross（proj stripped） | ❌ 崩溃 | — |

```
ValueError: not enough values to unpack (expected 2, got 1)
  sparse_structure_flow.py:278  global_cond, proj_cond = cond
```

**是脚本自身过时，不是产品 bug**：`dev/_bench_ss.py:155` 传 `attn_override="cross"`，
它只替换了 `blk.cross_attn` 这一个子模块，**没有改 `model.image_attn_mode`**，
模型仍按 `'proj'` 分支走 `sparse_structure_flow.py:273-278`，于是把单个 tensor
当成二元组解包。生产链路传的是 `{'global':…, 'proj':…}` 字典（273-276 行命中），
不受影响。修法：override 时同时设 `m.image_attn_mode = attn_override`。

```
  tokens   峰值MiB   净激活MiB   剩余MiB   注意力满矩阵MiB
     500      3562        331      1611              11
    1000      3771        541      1311              46

拟合: 净激活_MiB ≈ 0.5679·N + -0.00003829·N²
```

显存估算请用手册 §5.3 的解析公式。**

## 3. L1 端到端：从「HR 阶段 OOM」修到「只剩材质阶段」

### 3.1 三次运行对比

| 运行 | 条件 | 结果 |
|---|---|---|
| ① 原始 | 未改动 | ❌ 295 s 在 **HR 形状**阶段 OOM（申请 670 MiB，torch 仍报剩 3.53 GiB） |
| ② 只改 worker | 中间态 | ⚠️ 进入 HR 采样但**颠簸**：单步 25→24→49→**82 s**，功耗掉到 59~70 W |
| ③ 完整修复 | 启动器+app.py | ✅ HR 阶段 8 步稳定 **17.0~17.1 s**，功耗 117~145 W；❌ **材质阶段**失败 |
| ④ ③+关闭桌面程序 | 起始仅占 396 MiB | ❌ 同样在材质阶段失败（362 s） |

运行 ③ 的 HR 阶段合计约 **119 s**，比手册 §5.1 记录的 203 s 快了约 40%。

### 3.2 根因修复：`PYTORCH_CUDA_ALLOC_CONF` 被三处互相覆盖

```python
engine/code/app.py:5              os.environ['PYTORCH_CUDA_ALLOC_CONF'] = 'max_split_size_mb:128'
engine/code/pipeline_worker.py:97 os.environ["PYTORCH_CUDA_ALLOC_CONF"] = "garbage_collection_threshold:0.65"
engine/code/example.py:6          os.environ["PYTORCH_CUDA_ALLOC_CONF"] = "expandable_segments:True"
```

`os.environ[...] =` 是**整体替换**，后写的把前面的完全抹掉；而且这个变量在 CUDA
分配器初始化时只读一次，之后再改可能已经不生效。实测 `/proc/<pid>/environ` 证实
worker 进程启动时拿到的是 `max_split_size_mb:128` —— 那是给旧分配器的补丁，
会阻止大块复用。

三处都没开 `expandable_segments:True`，而**这正是 PyTorch 报错信息自己推荐的设置**。

**改动（3 个文件）**：

1. `_启动WSL后端.ps1` —— 在启动 env 列表里加
   `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True,garbage_collection_threshold:0.65`。
   放在启动时是**权威做法**：进程一起来就是正确值，不依赖 import 顺序。
2. `engine/code/app.py:5` —— 改成 `os.environ.setdefault(...)`，不再无条件覆盖启动器的值，
   并去掉 `max_split_size_mb`。
3. `engine/code/pipeline_worker.py:97` —— 与上面统一。

验证（运行 ③④ 日志第 15-17 行，`/proc` 的**初始**环境）：

```
pid 17: PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True,garbage_collection_threshold:0.65
pid 34: PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True,garbage_collection_threshold:0.65
pid 35: PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True,garbage_collection_threshold:0.65
```

> ⚠️ **顺带修的一个坑**：编辑工具写 `_启动WSL后端.ps1` 时把 **UTF-8 BOM 弄丢了**。
> PowerShell 5.1 对无 BOM 的 .ps1 会按 ANSI(GBK) 解码，中文注释的字节被吞掉换行，
> 导致整个脚本语法错误、后端**完全起不来**。已用 `UTF8Encoding($true)` 写回 BOM 并
> `Parser::ParseFile` 校验通过。**以后改这个文件务必确认 BOM 还在**
> （`_修复链接.ps1` 也是带 BOM 的）。

### 3.3 剩下的失败：材质阶段显存不够

```
[WORKER] image_cond_model_tex_1024: NAF 已加载
[MODEL] 按阶段从硬盘加载条件模型: image_cond_model_tex_1024
[VRAM] NAF 前把 DINOv3 挪到 CPU：剩余 3407MiB < 阈值 3500MiB，腾出后 6509MiB
[ERROR] Generation failed after 362s: RuntimeError: CUDA driver error: out of memory
```

- 此时设备占用 **7957 / 8192 MiB**，只剩 235 MiB；
- `dmesg` 新增 `dxgkio_make_resident: Ioctl failed: -12`（ENOMEM）；
- 起始桌面占用已压到 396 MiB（运行 ④），**仍然差最后一点**。

即：Pixal3D 材质阶段自身要约 **7.6 GB**，加桌面约 0.4 GB = 8.0 GB，
正好越过 8.192 GB 的上限。这不是代码算错，是**8 GB 卡的真实天花板**
（手册 §5.1 自己也说「显存峰值约 7.9 GB / 8 GB，贴着上限」）。

**关于「放不下就放内存」**：WSL2 其实**已经**在做这件事 —— 显存不够时驱动把页换到
系统内存，但那正是本次运行 ② 里 59~70 W / 单步 82 s 的「颠簸」，也正是你说的
「把宿主机卡死」的来源（`make_resident` 失败 + WDDM 超额订阅）。
**安全的做法是显式把模块放 CPU 再按需搬**，程序里已经有这个机制
（`_offload_backbone_for_naf()` 把 DINOv3 挪到 CPU，日志里 3407→6509 MiB 就是它），
只是目前只覆盖了 DINOv3，没覆盖材质阶段的 flow 权重。

## 5. 建议

按性价比排序：

1. **给材质阶段也做显式 CPU 卸载**（真正的修法，回答你的问题）。
   现在 `_offload_backbone_for_naf()` 只挪 DINOv3；材质阶段同理可以把
   `tex_slat_flow_model_1024` 按层/按阶段搬，或在该阶段把 shape 侧权重也挪走。
   目标是把这条阶段的 GPU 需求压到 ~6.5 GB。
2. **给材质阶段加和 HR 形状同款的降级路径**。HR 已经会 1024→896→768 自动降，
   材质阶段没有 → 不行就早失败、干净失败，而不是撞到驱动层 ENOMEM。
3. **修 `dev/_test_pixal3d.py` 的成功判定**（上面 §4 第 1 条）—— 否则这个「端到端测试」
   会把失败报成成功。
4. **短期绕开**：用 **TRELLIS.2 + 512**（手册 §1.3：约 5 分钟、峰值 4.4 GB），
   这条链路完全不碰材质阶段的瓶颈。
5. 桌面程序保持现在的精简；`vmIdleTimeout=15000` / `autoMemoryReclaim=gradual`
   这两个 `.wslconfig` 设置比较激进，若还遇到宿主机卡顿可以试着关掉
   `autoMemoryReclaim` 观察（本次未改动你的系统配置）。

## 7. 追加修复：按需给显存 + 进度条（第二轮）

### 7.1 让整个流程跑完 —— 自适应 NAF 目标尺寸

材质阶段失败的真正原因不是「上一步没卸载」（实测进入材质阶段时可用 7069 MiB，
上一步确实已经退回），而是**这一步自己就要 ~6.8 GB**：

```python
# pipeline_worker.py 的 IMAGE_COND_CONFIGS
"shape_1024": { ..., "naf_target_size": 512  },   # ← 这一步能跑
"tex_1024":   { ..., "naf_target_size": 1024 },   # ← 面积是上面 4 倍
```

NAF 上采样的显存 ∝ 目标面积 × 特征维数。1024² 相对 512² 是 **4 倍**，
所以只有材质阶段越界。手册 §4.3 其实已经点出这一点（"512²（shape_1024）
甚至 1024²（tex_1024）"）。

**改动**：`image_conditioned_proj.py` 新增 `_adaptive_naf_target()`，
在两处 NAF 调用前按当前可用显存选最大的装得下的档位
（1024→896→768→640→512→384→256），并用与实测吻合的系数估算：

```
need ≈ 3.0 × 特征维数 × 元素字节 × 目标边长²
```

tex_1024（D=1024, fp16, 1024²）估出 12288 MiB，与实际观测 ~6.3 GB 同量级。
实测本机降到了 **640²**：

```
[VRAM] NAF 目标 1024² 约需 12288MiB，当前可用 6529MiB（预留 768MiB） → 降到 640²
```

可以用 `PIXAL3D_NAF_ADAPTIVE=0` 关掉这个降级；`PIXAL3D_NAF_TEMP_FACTOR` 可调系数。

另外在 `pixal3d_image_to_3d.py` 加了 `_evict_idle_modules()`，在**进入材质阶段**和
**进入解码阶段**前把所有懒加载权重退回 CPU/磁盘（只处理带 `unload_to_disk()` 的
包装器，不会误伤在用模块）：

```
[VRAM] 按需回收闲置权重（进入材质阶段）: 可用 7049→7069MiB
[VRAM] 按需回收闲置权重（进入解码阶段）: 退回=['image_cond_model_tex_1024']
```

**结果：全流程跑通，7.8 / 8.0 分钟（手册记录约 12 分钟），返回体是真正的 3D 预览器。**
全程功耗 117~190 W，没有出现 60~70 W 的颠簸特征，结束后显存回落到 1.2 GB。

### 7.2 进度条为什么是摆设

`engine/code/_progress.py` 的 `_DESC_MAP` 用的是**精确匹配**：

```python
key = _DESC_MAP.get(desc)     # desc 实际带后缀
if key is None:
    return                    # ← 每次都从这里返回，什么都不写
```

而真实传进来的 `tqdm_desc` 全都带后缀：

| 实际 desc | 表里的键 | 旧结果 |
|---|---|---|
| `Sampling sparse structure (proj)` | `Sampling sparse structure` | ❌ |
| `Sampling shape SLat (proj)` | `Sampling shape SLat` | ❌ |
| `Sampling HR shape SLat (proj, 768)` | `Sampling shape SLat (HR)` | ❌ |
| `Sampling texture SLat (proj)` | `Sampling texture SLat` | ❌ |

**四个阶段一个都匹配不上**，所以 `report()` 永远在第一行返回，
`_progress.json` 只在 `decode`/`render` 这类 `stage()` 调用时才动一下 ——
看起来就是个摆设。

**改动**：改成取**最长前缀**匹配（`_key_for_desc()`），并顺手把 `app.py` 的
`_STAGE_ORDER` 从错误的 `[sparse, shape_lr, shape_hr, shape, ...]` 改成真实顺序
`[preprocess, sparse, shape, shape_hr, texture, decode, render]`。

验证（4/4 通过 + `report()` 确实写盘）：

```
OK    'Sampling sparse structure (proj)'  -> 'sparse'
OK    'Sampling shape SLat (proj)'        -> 'shape'
OK    'Sampling HR shape SLat (proj,768)' -> 'shape_hr'
OK    'Sampling texture SLat (proj)'      -> 'texture'
report() 写入 -> {'running': True, 'key': 'shape_hr', 'step': 3, 'total': 8, 'pct': 37}
```

真机运行中连续采样 `_progress.json` 也确认在动：

```
[17:50:12] step 1/8  pct 12
[17:50:24] step 2/8  pct 25
```
